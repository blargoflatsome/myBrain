# Project Instructions: My Brain

## 1. Overview

My Brain is an app where you store everything you need to remember. It is a personal productivity and "boredom buster" app that I can reach from anywhere (Android phone, iPhone, laptop and desktop). Its most important job is **instant capture**: whenever I have a thought, I can record it in a couple of taps, even offline.

### How to work: spec-driven development

This project is built **spec-first**. This document is the spec, and it is the source of truth for what to build. Follow these rules for the whole project:
- **Read only what the task needs.** What to read at the start of a session is in `CLAUDE.md` (kept short: key rules and commands, pointing here). Read section 10 (Phase 2/3) only when the task concerns it. This file is the only copy of the spec; update it, not any other.
- **Keep the spec updated.** When a decision changes, a requirement is clarified, or something is built differently than written, update `docs/SPEC.md` in the same change as the code. Never let the code and the spec disagree silently.
- **Spec first for changes.** When I ask for something new or different, say which parts of the spec will change and get my OK. Update the spec, then build it.
- **Don't guess.** If the spec is silent or unclear, ask me, then write the answer into the spec. When an open question in section 12 is answered, move the answer into the section it belongs to and remove the question.
- **Check against the spec.** Before calling a build step done, compare the work to the spec sections it covers. Name each Vitest and Playwright test after the rule it proves, and tell me about any rule that has no test yet.
- **Track progress.** `PROGRESS.md` holds only the current state (in progress, next, open items), linked to spec sections; update it at the end of each session and move merged work to `docs/PROGRESS_ARCHIVE.md`.
- **Log decisions.** Record significant decisions, and changes of mind, with the reason, at the end of `docs/DECISIONS.md`.
- **Keep the spec concise.** It holds rules and decisions, not code. Flag contradictions in the spec, or conflicts with current platform limits, instead of working around them silently.

It combines a daily checklist (routines, habits, tasks), a journal, "The Vault" for things to remember, a calendar/reminders view, a dashboard, and a Random Quest picker that chooses a project from my bucket list when I'm bored. Tasks are presented in the voice of "past you" (for example, "Past you left you this one").

## 2. Guiding principles
1. **Capture first.** Quick capture must be the fastest thing in the app. It asks where the thought goes: task, vault item, or quest.
1. **Works offline.** Capturing and checking things off must work with no connection and sync later.
1. **Multi-user ready.** I am the only user at first, but the app may become public someday. Every record belongs to a user and is protected by row-level security from day one.
1. **Free and open source.** Prefer free tiers and open source tools. Avoid paid or proprietary dependencies unless noted.
1. **Simple and documented.** Prefer simple, mainstream choices. Make small commits, keep a README that explains setup and key decisions, and explain notable trade-offs as you go.

1. **Confirm before impact; undo for the rest.** Anything that affects other people (cancelling or declining an event, deleting an event with guests, sending messages to others), removes many things or history at once (Delete my data, a bucket with items, a habit or routine with its history), or can't come back (Delete My Account) first shows a confirmation that says what will happen and who is affected. Removing **one** thing (a task, quest, Vault item, routine step, saved person, an availability time or one-off day (2026-11-24), or an event with no guests) and clearing lists (Clear crossed-off, Clear checked, marking a quest done) happen straight away, with **Undo in place** (2026-11-24, user; replaces the Undo bar), since deletes are soft and can be put back. The thing doesn't just vanish: its spot turns into a short line saying what happened, with an **Undo** button ("Deleted 'Buy stamps' · Undo"). Moving something off a list works the same (Tomorrow, Undated, Cancel task, Let it go, marking a quest done: "Moved 'Buy stamps' to tomorrow · Undo"), and a cleared list leaves one line where its button was ("Cleared 3 crossed-off tasks · Undo"). Where there's no row to stand in (an event in the calendar grid, an Orphan's card, a Post It, the Dashboard's Up next, a renamed tag), the line goes just under the heading of that page or card. **No timer:** a line stays until I leave the page (or close the window it's in), and each one keeps its own Undo, so a newer one never replaces an older one. **Focus:** I just pressed the trash can, Move or Clear, so focus moves to the line's Undo, which sits where I already was (with a mouse or a touch no focus ring shows). Deleted from an editor window, the window closes first and focus then lands on the line; a window closing never pulls focus away from it. After Undo, focus goes to the thing brought back (the row back in its place, the note shown on the Dashboard's Post Its, the card shown on Orphans), or the page's heading. Screen readers hear what Undo undoes (the line describes its button). Undo puts back **everything** the delete did, not only the row (2026-11-24): deleting the last Orphan counted toward Orphan wrangler, so its Undo takes that count back too. Routine actions like checking off a task or a quick capture need neither. Things that come by themselves (Cheers' "Share it in Cheers?" offer) are alerts under the bell and never take focus.
1. **Calm by design (ADHD-friendly, 2026-11-10).** The app is built for neurodivergent people and must never feel loud or urgent:
   - **Colours:** warm off-white (dark: deep slate) background, soft charcoal text, a soft blue accent, sage green for done. Priority dots are muted (Low sage, Medium soft ochre, High muted terracotta) and always come with their label. Red is kept for real errors and Delete My Account; Delete my data and Cancel event (it affects other people) are orange. Missed habits and "Most missed" use the muted style, never red (2026-11-12). Post It colours are pale.
   - **Icons:** plain outline icons in one style (like the tab bar), never colourful emoji.
   - **Text:** short and literal, readable at a skim: hints are at most one short line, or gone when the label says it; buttons say what they do ("Save task", "Delete quest"). Emphasis is bold, never italics or capitals. Body text has a line height of at least 1.5, is left-aligned, and reading pages keep lines to about 70 characters. The user's own playful lines stay as written; new wording is plain.
   - **Space:** generous padding and gaps, one main button per area, nothing crowded; optional fields are in More details (§5 Forms).
   - **Choices look alike everywhere:** a chosen option (weekdays, how often, energy, priority, answers, tabs, view switches) is a soft tint with a check mark, never a solid fill that looks like the main button. The same choice is the same control everywhere: Priority is one row of chips, **Low, Medium, High**, in Capture and every editor.
   - **Rows look alike everywhere (2026-11-12, user):** on every list row I can edit (tasks, habits, routines, quests, Vault items, Offsite connections), **tapping the title opens its editor**, and the row ends in a **trash can** that deletes it: straight away with Undo, or after a confirmation where §2 Confirm before impact asks for one (habits and routines with history). No separate Edit buttons. Rows may add their own actions before the trash can (Pick on quests, Cancel task on a task that keeps slipping). Journal days are the exception (2026-11-15, user): each past day has an **Edit** button (pencil and "Edit") at the right of its heading, since tapping the date wasn't obvious; the date is plain text, and days have no delete. Vault buckets open when tapped and are edited in their Settings.
   - **Buttons answer every press (2026-11-18, user: "Buttons should always give some kind of feedback when you click them"):** anything I can press dips slightly while pressed (a quick fade instead with reduce motion), so a tap always shows it landed. A button whose result isn't otherwise visible also says what happened: Cheers **Refresh** reads **Refreshing…** while it loads, then a short **"Up to date."** message fades in and out (the same message as the bell's "All caught up.", heard by screen readers).
   - **Adding looks alike everywhere (2026-11-12, user):** every list page has the same **+ New …** button (plus icon, soft accent outline, never solid) at the right of its heading: + New task, + New habit, + New routine, + New event, + New quest, + New bucket. Tasks also keep their quick-add box, because typing a title and pressing Enter is faster. **Inside a Vault bucket** there's no + New item (2026-11-12, user): its quick-add box (Add an item) is the way to add.
   - **Clickable things look clickable (2026-11-15, user):** every button, link and other control I can click shows the pointer cursor on hover; disabled ones don't.
   - **Check circles look alike everywhere:** crossing off a task, completing a habit and checking a Vault item use one control: a 44 px target with a 32 px circle and a drawn check mark (no text ✓).
   - **Motion:** nothing moves on its own; transitions are gentle and respect reduce-motion. The one kind of lively motion is a **celebration** right after I finish something (§5 Celebrations): short, never blocking, and toned down by reduce-motion or my Celebrations setting.
   - **Sound:** the app never plays sounds (2026-11-11). The one exception is the Focus timer's chime when a part ends, because it's an alarm I set.
1. **Accessible to everyone (WCAG 2.2 Level AA).** Every screen meets WCAG 2.2 Level AA: it works with a keyboard alone and with screen readers, has visible focus, enough color contrast in light and dark, tap targets of at least 24×24 px (44×44 px where practical), labels on every control, no meaning carried by color alone, text that can be enlarged to 200% and reflow at 320 px wide without losing anything, and motion that respects the device's reduce-motion setting. **Windows (modals) trap focus:** when one opens, focus moves into it and Tab / Shift+Tab stay inside it (a confirmation opened over an editor takes over until it closes); when it closes, focus returns to the control that opened it (or the page heading if that control is gone). This covers every window, the full-screen editor, and the phone menu (Escape closes it and returns to Menu). **The full-screen screens are windows too** (full-screen writing, the Focus timer, the priority reminder), so each one opens above any window already open, and Escape leaves full-screen writing without closing the window it was opened from (2026-11-15). Scrolling over a window or its dimmed background doesn't scroll the page behind it, where the browser supports that. **Every window has a close ✕ in its top right corner, and clicking outside it (on the dimmed background) closes it**, like Escape; a click that starts inside (selecting text) doesn't count. The priority reminder is the exception: only acting on it closes it. All new work keeps this: automated accessibility checks (axe) run on every page in the test suite, and anything they can't check is reviewed by hand.
1. **Long lists come in pages.** Any list that can grow long is shown a page at a time with a shared page control (Previous, "Page 2 of 5", Next), so pages never get endlessly long.
1. **Sort by dragging.** Anywhere I put things in my own order (routine steps, and any list added later), I drag them by a handle (⠿) with mouse or touch. The arrow keys on the handle move an item too, for keyboard use, and tapping the handle shows **Move up** and **Move down** buttons, so nothing needs dragging (WCAG 2.5.7).

1. **Credit (2026-11-12, user).** Every page ends with a footer: "Conceived of by Jordan Buermann © <this year>" (the current year, so it reads 2027 next year), the name linking to https://www.linkedin.com/in/jordanbuermann/ (opens in a new tab). It sits above the phone tab bar and clear of the Capture button. It stays in every copy of the project (CLAUDE.md "Credit in the footer").

### Voice and tone: "past you"
- The whole app speaks to the user in one consistent voice: it reminds them of what **past them** established. Nothing is ever the current user's fault. Past you made the plan, and present you gets to decide what to do about it. The tone is friendly and light, never scolding or guilt-inducing.
- Every message that asks the user to do something, or tells them something was missed, follows the same pattern: past you, what they established, then a gentle question or invitation.
- This applies everywhere the app speaks to the user: in-app text, empty states, push notifications, emails, texts to the user, and the Dashboard.
- Style examples (a guide for the voice, not a fixed list):
   - "Reminder: Past you asked that you journal today."
   - "Past you didn't check in yesterday. Would you like to do it now?"
   - "Past you agreed to this event. Are you going to go?"

- Write the rest of the messages in this same style for tasks, carried-over tasks, habits, routines, High tasks and priority habits, streaks, trophies, and event invitations and RSVPs. Keep all message wording in one place (a single file or table) so the voice is easy to adjust. Draft them and show me before finalizing.
- "Past you" is only for what I set up or did earlier. Something I'm doing right now is plain "you" ("You got unstuck!", never "Past you got unstuck") (2026-11-15).
- "Past you" only speaks to the user about themselves. Messages sent to other people, such as the standard cancellation text to guests and invitees, are written normally from the user to them.

## 3. Tech stack
- **Visual style:** calm, soft neutral colors with one accent color (soft blue), following §2 Calm by design. **Appearance (2026-11-12):** an Account setting, **System** (the default: light or dark following the device), **Light** or **Dark**, saved to my profile (`profiles.appearance`) and remembered on the device so it applies at once on the next visit, before sign-in finishes (sign-out forgets it, like everything else on the device).
- **Front end:** Vue 3 (Composition API) with Vite, Vue Router, and Pinia. Use TypeScript throughout (front end and server functions) and Tailwind CSS for styling, mobile-first.
- **PWA:** installable on Android, with a service worker (for example vite-plugin-pwa / Workbox), a web app manifest, home-screen shortcuts for quick capture, and Web Share Target so I can share text from other apps into the capture screen. A new version takes over as soon as it has downloaded (the app reloads itself, saving anything being typed first), so an installed app that stays open for days still gets updates.
- **Backend/data:** Supabase (open source; hosted free tier): Postgres, Google sign-in, row-level security, and Realtime for syncing across devices.
- **Server-side Node code:** Netlify Functions (including scheduled functions) for anything that must run on a server, such as sending push notifications. Verify current Netlify and Supabase free-tier limits before relying on them.
- **Offline storage:** IndexedDB (for example Dexie) with a queue of pending changes that syncs when online.
- **Calendar view:** an open source Vue calendar library (for example FullCalendar).
- **Notifications:** built-in Web Push (VAPID), plus in-app alerts. (ntfy was removed 2026-11-19, the user's choice.)
- **Hosting/deploy:** GitHub repository, auto-deployed to Netlify. Database schema lives in the repo as Supabase migrations.

### Testing, quality, and workflow
- **Dev test accounts (dev only):** `npm run dev:accounts` creates or resets three test accounts in the dev project only (Dev Alice, Dev Bob, Dev Carol; their shared password goes to `.env.local` and is never printed) so sharing and connections can be tried as more than one person. A dev-only password sign-in for them appears on the home page (signed out) only on the local dev server (`npm run dev`) with `VITE_DEV_SIGN_IN=true`, never in a production build; email/password sign-in is turned on in the dev project only, and production stays Google-only. `npm run test:flows` walks the connection and sharing flows against the real dev backend as those accounts and tidies up after. Both scripts refuse to run against production. Claude doesn't type passwords into the app itself (its safety rules); it runs `test:flows` instead.
- Use **Vitest** for unit and integration tests and **Playwright** for end-to-end tests in a real browser (including a phone-sized screen and, where possible, offline and installed-PWA behavior). **Phone runs are targeted (2026-11-11, user):** every browser test runs on desktop; Android and iPhone run only the tests that could fail differently on a phone (layout and navigation, touch and drag, native date/time and contact pickers, full-screen windows, text links, Safari's engine, accessibility scans). These are whole files listed in `playwright.config.ts` plus tests tagged `@phone`. A new test that depends on screen size, touch or the browser engine gets the tag.
- **Prove it works.** Tests for each feature as it is built: quick checks while coding, the full review (desktop, Android, iPhone) only at merge, so new work doesn't break old behavior without running everything every time. Fix any regression before moving on. How: `CLAUDE.md` Tests and CODING_STANDARDS §11. Long text covers everything I type (titles, notes, journal writing, Post Its, bucket names, tags, events); the mocked clock covers midnight rollover, carry-over, streaks, expired habit timers, timezones and daylight saving changes.
- GitHub Actions runs linting, type checking, Vitest, and Playwright on every pull request. **A pull request merges only once all its CI checks pass** (main requires them; 2026-11-24, user), and a browser test that passes only on a retry fails CI, because every flaky test looked into so far was a real bug. Before the full review, the branch gets a code review against CODING_STANDARDS. Netlify deploy previews are used for branches, and the main branch is production. **Merge to main once per build step** (one production deploy per step), because the Netlify free plan allows only about 20 production deploys a month (see Decisions). Work happens on a branch per step, tried out through its deploy preview.
- Use two Supabase projects, one for development and one for production (verify the free tier allows this), with migrations stored in the repo.

## 4. Data model (all tables have `id`, `user_id`, `created_at`, `updated_at`, and deleted_at (soft delete, so deletions sync to other devices), with row-level security so users only access their own rows. updated_at is set by the server, not the device clock. A few server-only logs and rate-limit counters keep only what they need.)
Matches the migrations as of 2026-11-24 (docs review). Planned tables that were never built are left out.

**Me**
- **profiles:** timezone, email and phone number (both required at signup), display name and avatar, appearance, celebrations (full, gentle or off), quiet hours, default snooze length, whether quiet hours also silence priority reminders (off by default), Web Push on, evening reminder time, focus room (on by default), sharing my free/busy times, my two cancellation messages (§5 Cancelling an event or attendance), and when I last used Delete my data.

**Tasks, habits and routines**
- **tasks:** title, notes, due date, priority (Low, Medium, High), reminder_time (High tasks with a date only; 2026-11-18), status (open, done, cancelled), completed_at, cleared_at (hidden from the list by Clear crossed-off), source (manual, capture, journal). Carry-over is worked out from the due date, never stored (§5 Tasks).
- **habits:** title, start date, how often and weekdays, reminder time (`notify_time`), timer duration (how long I have to complete it; an expired timer counts as a miss), priority flag, cached current streak and best streak (the source of truth is habit_logs, so streaks can always be recalculated).
- **habit_logs:** habit id, date, status (completed or missed), completed_at (so history and streaks can be recalculated and stats survive).
- **habit_pauses (2026-11-12):** start date, end date (empty while paused): the days Pause all streaks was on (§5 Habits).
- **routines:** title, reminder time, weekdays and every week or every 2 weeks (or none, for a run-anytime routine), start date. **routine_steps:** routine id, position, title or a link to one of my habits, the day it was added.
- **routine_runs / routine_step_logs:** per day (or per run, for run anytime), which steps were completed or skipped, for completion stats.
- **reminder_state:** per reminder and day: snoozed until, cancelled, last sent (written by the server job).

**Writing and remembering**
- **journal_entries:** date (one entry per day), body text, "tomorrow" text, the yes/no answer, auto-generated stats snapshot for that day (`stats`, JSON), whether the stats are final (`stats_final`), and whether the app wrote the entry on my behalf (`auto`). **Journal lock (2026-11-13):** `word_count` and `has_writing`, worked out from the writing by the app at every save and kept readable for everyone (locked or not), so streaks, trophies, Up next and the reminder never need the writing itself. When my journal is locked, `body` and `tomorrow` are stored encrypted (`enc:v1:…`, §5 Locking my journal).
- **journal_keys (2026-11-13):** one per person who locked their journal: my journal key, wrapped once by my passphrase (with its salt and round count) and once by my recovery key. Useless without one of them. Only I can read it.
- **journal_passkeys (2026-11-13):** passkeys that can unlock my journal: credential id, a name ("Pixel 8", "Work laptop"), the PRF salt, and my journal key wrapped by that passkey. Only I can read them.
- **post_its:** sticky notes for the Dashboard: body (formatted HTML, like the journal), color (yellow, blue or green; older notes may be pink) and position (lowest first; a new note goes in front).
- **vault_buckets / vault_items:** my buckets and the items inside them. A bucket has a name, whether its items can be checked off, starred, whether it's my default bucket (2026-11-20), and whether it shows on my profile. An item has a title, notes, an optional star rating (1–5), an optional link or address, whether it is checked, and `added_by`. **vault_shares** (who a bucket is shared with) and **vault_stars** (my star and default on a bucket shared with me): §5 The Vault, Shared Vaults.
- **quests:** title, details, time needed, energy needed, status (open or accepted; a done quest goes back to open), last_picked_at, times_picked, completed_at (the last time). **quest_logs:** quest id, date, completed_at, one per time a quest was done (for stats).
- **inbox:** my Orphans: raw captured text that hasn't been filed yet (§5 Quick capture). The table keeps its old name.
- **tags / item_tags:** user-defined tags (a name, unique per user ignoring case) attached to tasks, habits and routines.

**Trophies**
- **badges:** my earned trophies, one row per trophy, with its level (`tier`; empty for Firsts) and the day each level was earned (`levels`); the id is made from my user id and the trophy, so it's the same on every device. The table keeps its old name (§5 Trophies).
- **activity_log:** what the app didn't otherwise keep, for trophies: finished Focus sessions, finished Breathes, captures and emptying Orphans.

**Events and people**
- **events:** title, notes, start, end (or all day), repeat (never, daily, weekdays, weekly, every 2 weeks, monthly, yearly), reminder (none, or minutes before the start), show me as (busy or free), status (active or cancelled), cancelled_at, and whether guests can see who's going.
- **event_invites:** one per invitee: the event, the host's name, a name, an email and/or phone number, their answer (pending, yes, maybe, no, or dropped out) and when, whether they're optional, whether they show to other guests, and for guests a secret answer link (stored hashed). **invite_recipients:** which account an invite reaches, for connections (kept server-side, never shown to the host). The host sees their invitees and answers; an invitee sees only their own invite.
- **people:** my Offsite connections: name (optional), email, phone (at least one of the two). Synced like everything else; only mine.
- **availability_rules:** my weekly times I'm not available (weekday, from, until). **availability_exceptions:** one-off days (all day or from–until, not available or available after all).
- **outbound_messages:** every push and every one-at-a-time message to someone about an event (who, how, kind, when, status, error), written by the server. **message_optouts:** email addresses and phone numbers that asked not to be messaged.
- **connection_requests, connections, connection_blocks, connect_links, connect_code_tries:** §5 Connections.

**Cheers and focus**
- **cheer_posts (2026-11-15):** kind (did it, stuck, unstuck), text (up to 140 characters; empty for stuck), created_at; readable by every signed-in person through a server function that never returns the author. Gone from the feed after 48 hours.
- **cheer_reactions:** post id, reaction (one of the four), one per person per post, never on my own post. Only the post's author can read the counts.
- **cheer_blocks:** whose posts I've hidden, stored server-side from the post I blocked from; I never see who it is.
- **cheer_tally (2026-11-15):** my own totals for the Cheering others on trophies (reactions given, days I cheered, first reactions, people I cheered on who got unstuck, and whether I cheered while I was stuck), kept by the server as I react so they outlast the 48-hour posts. Only I can read mine, and it never says which posts.
- **focus_presence:** one row per person while their Focus timer runs: last check-in, the part (work or break) and when the part ends. Only anonymous dots ever leave the server. Rows older than a few minutes are ignored and cleared.

**Alerts and push**
- **notifications:** my alerts (the bell): kind, title, text, link, when sent. Kept 7 days.
- **notification_log:** server-only record of each push sent, so nothing is sent twice.
- **push_subscriptions:** user id, device label, push endpoint and keys, last_seen. One per device (phone, laptop); remove subscriptions that the push service reports as invalid.

- **Search:** runs on the device's own copy of my data (see Global search and tags).

## 5. Phase 1 features and rules

### Quick capture
- One-tap access from the home screen shortcut and a persistent button in the app. In the app, Capture opens as a window over the page I'm on, so it never takes me away (for example, I can add tasks while writing in my journal); closing it returns me exactly where I was. The home screen shortcut and text shared from other apps open the Capture page.
- **The text box comes first (2026-11-12):** Capture opens with the text box focused, so I can start typing at once. The type chips (Task, The Vault, Quest, Habit, Post It, Decide later) sit under it with **Decide later chosen**, so Save with no other chip saves to Orphans. Choosing a chip shows that type's fields below and keeps what I typed: the first line becomes the title and the rest the notes or details (between two types that both have a title and notes, both stay as they are). Only the title is required; everything else is optional or has a default, and optional details sit in **More details** (see Forms):
   - **Task:** Title, Date (blank = the Undated list), Notes (formatted), Priority (default Low), all in view.
   - **The Vault:** Title, Bucket (pick one, or make a new one; the first bucket in the list is preselected, which is my default bucket when I have one, §5 The Vault), Notes (formatted), and More details with rating and link, the same as the item editor.
   - **Quest:** Title; then Energy needed (default Ugh), Time needed (default 30 min) and Details (formatted), all in view with extra space between them (no More details).
   - **Habit:** the full habit form, laid out like the habit editor (see Habits).
   - **Post It:** a small formatted text box (the journal's editor, smaller, in place of the text box) and a color (yellow by default, or blue or green; pink was removed, and older pink notes still show pink). No title; the note itself is required. It goes to the top of the Dashboard.

### Locking my journal (end-to-end encryption, agreed 2026-11-13)
- **Why:** without it, the journal is plain text in the database, so the app's owner, anyone holding a service key, a stolen backup or a database breach can read it. Locked, my writing and "How to make tomorrow better?" are encrypted in my browser before upload, and nobody but me can read them, including the app's owner.
- **Opt-in:** **Lock my journal** in the Account page's Account Settings group (moved from Your data, 2026-11-13, user). Off by default. Journal only (not Vault notes, Post Its or other notes).
- **What's encrypted:** `body` and `tomorrow`. **Still readable on the server:** the date, the stats, the yes/no "Was today better than yesterday?" answer, `auto`, `word_count`, `has_writing`, and the tags on an entry. An empty field stays empty (not encrypted), so entries the app writes for me need no key.
- **Where:** only at the sync boundary (upload, pull, Download my data). The device's own copy stays plain text, so every feature reads it as before, and sign out deletes it (§5 Account page).
- **Keys:** the browser makes a random journal key (AES-256-GCM) and saves it in `journal_keys`, wrapped by:
  - **my passphrase**, chosen separately from Google sign-in (at least 12 characters, entered twice with a note under the second box saying as I type whether they match, a **Show passphrase** checkbox, `autocomplete="new-password"` so password managers save it, paste allowed). PBKDF2-SHA-256 with 600,000 rounds and a random salt, using the browser's WebCrypto. Not Argon2, which would need WebAssembly and a CSP change.
  - **my recovery key**: 24 random characters in groups of four, shown once, with Copy, Download (.txt) and Print, read out letter by letter for screen readers. I must tick "I saved my recovery key" to continue.
  - **any passkeys I add** (below).
- **Each field** is AES-256-GCM with a fresh 12-byte IV, stored as `enc:v1:<base64(iv ‖ ciphertext ‖ tag)>`. The additional data is `user_id | entry id | field`, so text can't be moved into another entry or field.
- **Unlocking:** each device asks once. The key is then kept on that device as a **non-exportable** WebCrypto key in IndexedDB until sign out, which deletes it. Unlocking works offline (`journal_keys` and `journal_passkeys` sync like other tables). The **Unlock your journal** box offers **Unlock with a passkey** first (when I have one and this browser supports it), then the passphrase, then "Use my recovery key instead". After 5 wrong tries it waits 30 seconds.
- **Passkeys (WebAuthn PRF), built now with the rest:**
  - Optional. Offered at the end of setup ("Add a passkey so Face ID or your fingerprint unlocks your journal", skippable), and in Account under Lock my journal: **Add a passkey**, and a list of my passkeys (name, date added, **Remove**). I can have several (phone, laptop). Synced passkeys (iCloud Keychain, Google Password Manager) unlock new devices too.
  - Adding one creates a passkey for the app's site with the PRF extension and user verification required, then reads a PRF output with a random per-passkey salt. HKDF turns it into a key that wraps the journal key, saved in `journal_passkeys`. If the browser or authenticator doesn't return PRF, nothing is saved and it says "This device can't unlock your journal with a passkey. Your passphrase still works."
  - Passkeys only unlock the journal. They don't sign in (Google sign-in is unchanged) and need no server check, since only the device can produce the PRF output.
  - The passphrase and recovery key stay required, because passkeys can be lost and PRF isn't supported everywhere. **Unlock with a passkey** shows only where `PublicKeyCredential` exists, and falls back calmly if it fails. Passkeys belong to one site address, so production, dev (localhost) and Netlify previews each have their own.
- **While locked** (a device that hasn't been unlocked): the Journal shows dates, stats and yes/no answers, with an Unlock box in place of the writing and editors (new writing needs the key). Until a device has downloaded my lock (a new device's first sync), the Journal says "Checking whether your journal is locked…" in place of the editors, so nothing is typed before it knows. Search leaves journal entries out and says "Unlock your journal to search it". Trophies, streaks, the dashboard, Up next and reminders work as usual from `has_writing` and `word_count`. Download my data asks to unlock first; **Skip** exports the encrypted text with a note in the file (`journal_note`). A field that fails to open (wrong key, tampered) shows a calm message instead of the writing.
- **Turning it on** encrypts and re-uploads every existing entry, with a progress line ("Locking 143 entries…"); it finishes in the background. The setup says older copies on the server are gone within about a week (backups expire).
- **Change passphrase / New recovery key / Add a passkey** (Account) first ask me to show it's me (passphrase, recovery key or a passkey). Only the journal key is re-wrapped; no entry is re-encrypted. Removing a passkey offers Undo.
- **Forgot everything:** **Start my journal over** permanently deletes the encrypted writing on every entry (dates, stats, answers, word counts and trophies stay) and my passkeys, then sets up a new passphrase. Confirmed by typing DELETE.
- **Turning it off** needs the passphrase, recovery key or a passkey, and confirms ("Your journal will be readable on the server again."). It decrypts and re-uploads every entry, then deletes `journal_keys` and `journal_passkeys`.
- **The server refuses plain text** once I've locked my journal: a trigger requires `body` and `tomorrow` to be empty or start with `enc:v1:` while I have a live `journal_keys` row, so an old cached copy of the app can't upload plain writing (the sync engine keeps refused changes and retries them).
- **Server size limit:** the inputs still allow 200,000 characters of writing and 20,000 for "How to make tomorrow better?". The server allows up to 1,100,000 and 120,000 for encrypted text.
- **What it doesn't protect against** (said on the Privacy page): a malicious app update (whoever controls the code could capture passphrases), an unlocked device in someone else's hands, and the readable facts listed above.
- **Delete my data** (journal part) and **Delete account** also remove `journal_keys` and `journal_passkeys`.
- **Code:** `src/journal/crypto.ts` (keys and fields), `keyring.ts` (this device's key), `lockingRemote.ts` (the sync boundary), `passkeys.ts`, `lockActions.ts`, `lockRules.ts`, `useJournalLock.ts`; screens in `src/journal/components/` (`JournalLockCard`, `JournalLockDialog`, `UnlockForm`, `UnlockJournal`, `PassphraseFields`, `RecoveryKeyShow`). Migration `20261113010000_journal_lock.sql`.
- **Tests:** crypto unit tests (round trip with the long-text samples; wrong key, changed byte or moved text fails; passphrase, recovery key and passkey each unlock; changing the passphrase keeps entries readable); `word_count`/`has_writing` match `plainText()`; sync integration (no plain writing in any upload, pulls decrypt, a locked device stays locked); `src/tests/e2e/journal/journal-lock.spec.ts` (setup, unlock on a new device, recovery key, wrong passphrase, search while locked, Start over, turn off, a network check that no request contains the typed writing; passkeys through Chromium's virtual authenticator with PRF, desktop only); axe checks of the new dialogs at 320 px; `src/tests/db/rls_journal_lock.sql` (RLS on both tables, the plain-text trigger, reminders use `has_writing`, delete functions).

## 7. Offline and sync
- Reads come from the local store first; writes are applied locally and queued.
- Sync on reconnect and via Realtime; resolve conflicts simply: **the last edit to reach the server wins** (the server sets `updated_at` on arrival). An older offline edit that syncs late can overwrite a newer edit from another device; this is accepted for Phase 1.
- Show a small online/offline/syncing indicator.
- **Locked journal (2026-11-13):** journal writing is encrypted on upload and decrypted on pull at the sync boundary; the device's own copy is plain text (deleted at sign out). A device that hasn't unlocked keeps pulled writing encrypted until it does (§5 Locking my journal).
- **Catching up and not leaving changes behind.** Coming back to the app (opening it, or switching back to it) uploads anything queued and pulls what changed, because Realtime misses changes while a device sleeps. Switching away from the app saves anything waiting to be saved (such as writing saved on a short timer) and uploads it straight away, because a phone may stop a hidden app. Changes still queued are retried every 30 seconds while the app is open, since a dropped request on a weak signal doesn't count as going offline.

- Deletions are soft deletes (a `deleted_at` value) so they sync to other devices, and `updated_at` is set by the server rather than the device clock. Once per app start, after a sync, rows deleted over 30 days ago are removed from the device (alerts, habit logs, tag links, Post Its, Orphans, Offsite connections and quest logs), unless a change to them is still waiting to upload. Deleted tasks, habits, events, Vault items and quests stay, because trophies count them.
- **Things only the server can do (2026-11-24, user)** (invitations, cancelling, sharing a bucket, connections, Cheers, profiles, the Focus room) need a connection. Offline, they don't try: the screen says it needs the internet. When one goes through, my own copy of what it changed (my events, invitations, shared buckets) is brought up to date straight away, without waiting for a sync. When one fails, the screen says so in its own plain words (never the server's raw error text), and a limit says which limit (25 people per event, 100 invitations or 50 messages a day, 20 connection requests a day, 5 connect links at a time, 25 people per bucket, Cheers posts).
- **Lists from the server (2026-11-24, user)** (Cheers, Connections, who on my Offsite connections has an account, an event's invitees) load when I'm online and again when I come back online, so a page opened offline fills in by itself. A list that couldn't load says so calmly, with **Try again**, instead of looking empty; one that loaded before keeps showing while a later try fails.
- Actions that notify other people (cancelling, declining, invitation messages) need a connection. If I am offline they show as pending, and I am asked to confirm again when I reconnect, so nothing goes out late by surprise.
- Sync layer: a simple custom queue on Dexie (IndexedDB). Record ids are generated on the device, so retried uploads never create duplicates. Changes are pulled by `updated_at` since the last sync (a copy the device already has isn't written again, so screens don't redraw for nothing), plus Realtime for live updates. Queued changes to the same table upload together, up to 50 per request; if the server refuses a batch, they're sent one at a time so only the refused one is marked. A change the server refuses is kept and retried on every sync (app start, reconnect), never dropped. Evaluated and rejected: RxDB (free tier allows only 13 open collections; paid from $99/month) and PowerSync (extra service and account, free instances deactivate when idle, harder for Pi device pairing).

## 8. Auth and security
- Google sign-in through Supabase Auth.
- Row-level security on every table. Never expose service keys in the front end; keep secrets in Netlify environment variables.
- **Everything people type is untrusted** (security sweep, 2026-11-07). The rules:
  - **Shown as text, never run as code.** Typed text is displayed as plain text everywhere (Vue escapes it). Formatted writing (journal, "tomorrow", Post Its) is cleaned with DOMPurify to the editor's own formatting before it's shown: no scripts, event handlers, styles, frames or forms; the only input kept is a checklist box; links may only be web, email or phone links and open safely in a new tab. A Vault link that isn't a web address opens a map search, so it can never be a script.
  - **Security headers** on every page (`public/_headers`, also sent by the test server so every browser test runs under them): a strict Content Security Policy (scripts only from the app itself, no inline scripts, connections only to the app and Supabase, pictures only from the app and Google profile photos, no framing, no plugins), plus nosniff, no framing, a strict referrer policy, HTTPS only, and camera/location off (microphone allowed for the Capture speech button).
  - **Size limits on the server** for every text column people type into (titles 500 characters, notes 20,000, names 120-200, journal writing 200,000), matched by limits on the inputs. A title that's too long when filing moves the rest into the notes.
  - **Addresses:** profile pictures and push addresses must be https; push is only ever sent to real browser push services (Google, Mozilla, Apple, Microsoft), so a stored address can't make our server send requests elsewhere. The push sender checks its shared secret in constant time and handles at most 50 devices per call.
  - **Database:** every query is parameterized (no SQL is built from typed text); every table has row-level security; server functions run with a fixed search path and check sizes, permissions and rate limits; people search ignores wildcard and escape characters.
  - **Other:** calendar files escape every kind of line break and quote names; redirects only go to pages inside the app; tapping a notification only opens the app; secrets stay in environment variables and Supabase Vault.
  - **Tests:** `src/tests/e2e/security/security.spec.ts` (headers, no blocked resources on any page, script-injection attempts in every place typed text is shown, including the public guest page), `src/tests/unit/security/security.test.ts`, and `src/tests/db/rls_security.sql`.

Every other response carries `X-Robots-Tag: noindex, nofollow` (`public/_headers`), including the pages that must work without an account (the guest invitation page, whose address holds a private token, and Privacy and Terms). `robots.txt` lets crawlers in (so they can read the noindex) and names no private paths. Signed-in pages show nothing until sign-in anyway.
  - **Search listing and 404s (2026-11-12, user):** the home page has a canonical link to itself, and the build writes a one-page `sitemap.xml` (the home page) named in `robots.txt`, both with the site's own address (Netlify's `URL` when it builds, so a copy uses its own). ## 13. Accounts, services, and credentials

Before building, walk me through creating each account below. Ask me for the credentials and API keys when they are first needed, and do not assume you already have access to anything.

### Rules for handling credentials
- Ask me for each credential at the moment it is first needed. Tell me what it is for, where to find it, and which permissions or scopes to give it. Use the least access that works.
- Prefer login flows over pasted secrets when a command line tool offers one (for example `gh auth login`, `netlify login`, `supabase login`).
- Store secrets only in a local `.env.local` file that is listed in `.gitignore`, and in Netlify environment variables for the deployed app. Never commit secrets to GitHub, never print them in logs or output, and never put them in front-end code.
- Only the Supabase anon (publishable) key may be used in the browser. The Supabase service role key, the Google OAuth client secret, and the VAPID private key are server-side only (Netlify Functions).
- Provide a `.env.example` file listing the variable names without values, and document in the README where each one comes from.
- If a key is ever exposed, tell me right away and walk me through rotating it.

### Services needed for Phase 1
- **GitHub** (https://github.com): hosts the code. Needed: an account, a new repository, and a way for you to push (GitHub CLI login, or a personal access token limited to that repository). Netlify deploys from this repository.
- **Netlify** (https://www.netlify.com): hosts the web app and runs the server-side functions, including scheduled ones. Needed: an account, a site linked to the GitHub repository, and environment variables for the secrets below. Verify the current free-tier limits.
- **Supabase** (https://supabase.com): database, Google sign-in, row-level security, and realtime sync. Needed: an account, a new project, the project URL, the anon key (browser), the service role key (server only), the database password, and an access token if you use the command line tool for migrations.
- **Google Cloud Console** (https://console.cloud.google.com): provides the OAuth client used for Google sign-in through Supabase. Needed: a project, the OAuth consent screen, a web OAuth client ID and secret, and the redirect URL that Supabase provides.
- **Web Push keys (VAPID):** no account needed. Generate the key pair yourself; the private key is server-side only.

### Services for later phases
- **Domain name:** none for now (decided 2026-11-06). The app uses its free Netlify address, https://myadhdbrain.netlify.app. Worth buying one before Google's OAuth verification for a public app, which works much better with an owned domain.
